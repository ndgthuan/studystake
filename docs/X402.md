# StudyStake — x402 Study Credential spec

Source of truth for the x402 track. When in conflict with [`AVALANCHE_PLAN.md`](AVALANCHE_PLAN.md) (P1) or [`ORACLE.md`](ORACLE.md), this file wins.

**Status:** the API below is not implemented yet. Field names, routes and the EIP-712 type are fixed here so every later task can build against them.

## 1. What is sold, and why

Badge stats are public on-chain, so anyone can read them for free. A StudyStake credential sells what the chain cannot prove on its own:

> The oracle attests that this wallet is bound one-to-one to a real LMS account on a given site, with these on-chain results, at this time.

The buyer gets a signed statement it can store, forward and verify later without calling us. The student controls whether it can be sold at all, and the revenue funds the next reward pool.

| Actor | Does |
|---|---|
| **Student** | Opts in with a wallet signature. Can opt out at any time. |
| **Buyer** (scholarship app, recruiter, AI agent) | Pays USDC per request. Needs USDC only, no AVAX. |
| **Oracle Worker** | Checks consent, asks for payment, signs the credential. |
| **Facilitator** | Verifies the payment signature, submits the USDC transfer, pays gas. Holds no funds. |
| **Treasury** | Receives the payment. Uses it to `sponsor()` later challenges. |

## 2. Request flow

```
Buyer                       Oracle Worker                 Facilitator          Fuji
  │ GET /x402/credential/:wallet │                             │                 │
  │─────────────────────────────▶│ checks: rate limit, linked, consent           │
  │ 402 + PAYMENT-REQUIRED       │                             │                 │
  │◀─────────────────────────────│                             │                 │
  │ signs EIP-3009 (no tx)       │                             │                 │
  │ GET + PAYMENT-SIGNATURE      │                             │                 │
  │─────────────────────────────▶│ POST /verify                │                 │
  │                              │────────────────────────────▶│                 │
  │                              │ reads badge, signs credential                 │
  │                              │ POST /settle                │                 │
  │                              │────────────────────────────▶│ transferWith... │
  │                              │                             │────────────────▶│
  │ 200 + PAYMENT-RESPONSE       │                             │                 │
  │◀─────────────────────────────│                             │                 │
```

Rules that follow from this order:

1. **Free checks come first.** A wallet that is not linked or has not consented is refused before any payment is asked for, so a buyer never pays for nothing.
2. **The credential leaves only after settlement.** The Worker builds it after `/verify`, but returns it only when `/settle` succeeds. Otherwise a buyer whose transfer fails would get it for free.
3. **Failing before settlement charges nothing.** If reading the chain fails after `/verify`, the Worker returns `502` and never calls `/settle`.

## 3. Endpoints

All routes live in the oracle Worker and follow its conventions: `snake_case` fields, errors as `{error: {code, message}}`, addresses matching `^0x[0-9a-fA-F]{40}$`.

### `GET /x402/credential/:wallet` (paid)

| Situation | Status | Body / headers |
|---|---|---|
| x402 not configured | `503` | `x402_disabled` |
| Too many requests from this IP | `429` | `rate_limited` |
| Malformed wallet | `400` | `invalid_wallet` |
| Wallet has no LMS link | `404` | `not_linked` |
| Student has not consented, or relinked since | `403` | `credential_not_shared` |
| No or invalid `PAYMENT-SIGNATURE`, or verification refused | `402` | `PAYMENT-REQUIRED` header, see section 4 |
| Header larger than 8 KB | `413` | `header_too_large` |
| Chain or facilitator unreachable | `502` | `upstream_error`, not charged |
| `/settle` fails | `402` | `PAYMENT-REQUIRED` header with `error` set, not charged |
| Paid | `200` | `PAYMENT-RESPONSE` header, body below |

Success body:

```json
    "lms": "moodle",

    "site_hash": "0x7c43f8cc8eb07260bc7a877fea2a58b10f537694ec543ecfb350c95321c0c5c2",
    "streak": 3,
    "best_streak": 5,
    "total_completed": 7,

    "issued_at": 1794000000,
    "expires_at": 1794604800
  },
  "signature": "0xe580f50b…3bc3961b",
  "signer": "0x70997970C51812dc3A010C7d01b50e0d17dc79C8",
  "domain": {

  },
  "transaction": "0x…"

```

A linked wallet with no badge yet gets a credential with all stats at `0`. That is a true statement, not an error.

### `GET /x402/credential/:wallet/consent` (free)

Returns `{ "wallet": "0x…", "share": true }`. Used by the `/link` page and by buyers who want to check before paying.

### `POST /x402/credential/consent` (free, signed)

```json
{ "wallet": "0x…", "share": true, "signature": "0x…", "issued_at": 1794000000 }
```

The wallet signs this EIP-191 message, built by `consent_message` in `link.ts`:

```
StudyStake credential consent
wallet: <lowercase address>
share: <true|false>
issued_at: <unix seconds>
```

It uses the existing freshness window (`check_issued_at`, 10 minutes), a replay nonce (`nonce_key` with purpose `consent`) and the IP rate limit. Refused with `404 not_linked` if the wallet has no link.

### `GET /x402/stats` (free)

Returns `{ "pay_to": "0x…", "asset": "0x…", "price": "5000", "settled_count": 12, "settled_amount": "60000" }`. Used by the admin revenue panel. The counters live in KV and are best effort, because KV is not atomic. On-chain USDC transfers remain the real record.

## 4. Payment format

x402 version 2, scheme `exact`, as used by the organizers' [starter](https://team1vn.xyz/demos.html#x402-pay-per-request) with `@x402/*` pinned at 2.28. The example below was validated against `parsePaymentRequired` and the header codec of `@x402/core@2.28.0`.

All three headers carry **base64 of the JSON** (standard alphabet).

**`PAYMENT-REQUIRED`** (with `Cache-Control: no-store`). Clients read this header, not the response body:

```json
{
  "x402Version": 2,
  "error": "payment required",
  "resource": {
    "url": "https://<oracle>/x402/credential/0x90F7…b906",
    "description": "Signed StudyStake study credential",
    "mimeType": "application/json"
  },
  "accepts": [{
    "scheme": "exact",
    "network": "eip155:43113",
    "asset": "0x5425890298aed601595a70AB815c96711a31Bc65",
    "amount": "5000",
    "payTo": "<treasury address>",
    "maxTimeoutSeconds": 120,
    "extra": { "name": "USD Coin", "version": "2" }
  }]
}
```

- `amount` is in USDC base units: `5000` = 0.005 USDC.
- `extra.name` and `extra.version` must match the token's EIP-712 domain. We read `name()` = `USD Coin` and `version()` = `2` from Circle USDC on Fuji. The library does not know this token on Fuji, so they must be stated.
- These names are defined by x402, so they stay camelCase here, unlike the rest of the API.

**`PAYMENT-SIGNATURE`**: the buyer's `PaymentPayload`, which is `{ x402Version, resource?, accepted, payload }`. The Worker treats `payload` as opaque and forwards it.

**`PAYMENT-RESPONSE`**: the facilitator's `SettleResponse`, which holds `{ success, payer, transaction, network }`. The Worker also copies `transaction` into the body.

### Facilitator calls

Both are `POST` with `{ x402Version, paymentPayload, paymentRequirements }`.

| Path | Response | Worker behavior |
|---|---|---|
| `/verify` | `{ isValid, invalidReason?, payer? }` | `isValid: false` → `402` |
| `/settle` | `{ success, errorReason?, transaction, network, payer? }` | `success: false` → `402`, credential discarded |

`paymentRequirements` is **always built by the Worker from its own config**, never taken from the buyer's `accepted` field. This stops a buyer from signing a smaller amount or a different recipient.

Each call has a 10-second timeout. Calls are not retried, because a retried settle could look like a failure after the money moved.

## 5. The credential (EIP-712)

**Domain:**

```
name:              "StudyStake Credential"
version:           "1"
chainId:           CHAIN_ID
verifyingContract: MANAGER_ADDRESS
```

**Type:**

```
Credential(
  address wallet,
  string  lms,
  bytes32 subject_hash,
  bytes32 site_hash,
  uint32  streak,
  uint32  best_streak,
  uint32  total_completed,
  uint32  total_failed,
  uint64  issued_at,
  uint64  expires_at
)
```

| Field | Source |
|---|---|
| `wallet` | The route parameter, checksummed |
| `lms` | `LinkRecord.lms`: `moodle` or `demo`. **Buyers must reject `demo`** when they need a real student |
| `subject_hash` | `LinkRecord.subject_hash` = `keccak256("<site>\|<userid>")`, the same value published in evidence |
| `site_hash` | `keccak256(utf8(LinkRecord.site))`, so a buyer can compare it with the school it expects |
| `streak` … `total_failed` | `StudyBadge.stats_of(badge_of(wallet))`, read from the address in `manager.badge()`. All `0` when there is no badge |
| `issued_at` | Worker clock, unix seconds |
| `expires_at` | `issued_at + 604800` (7 days), so stats cannot stay valid forever |

It contains no name, student ID, raw userid or token.

**Signing key:** `ORACLE_PRIVATE_KEY`. It already holds `ORACLE_ROLE`, and buyers can check that role on-chain. No new secret is needed.

### How a buyer verifies

1. Recover the signer from the typed data and `signature`.
2. Check `manager.hasRole(ORACLE_ROLE, signer)` on-chain. Revoking a compromised oracle therefore invalidates its credentials for every verifier.
3. Check `domain.chain_id` and `domain.verifying_contract` are the deployment you trust.
4. Check `now < expires_at`.
5. Check `lms` is `moodle` and `site_hash` matches the expected school.

The `/credential/verify` page does exactly this, and also shows live badge stats next to the signed ones.

## 6. Consent

Stored in KV at `consent:<lowercase wallet>`:

```json
{ "share": true, "subject_hash": "0x…", "updated_at": 1794000000 }
```

- **Off by default.** No record means no sale.
- **Tied to the subject.** The stored `subject_hash` must equal the current link's. Linking the wallet to another account voids old consent.
- **Removed on unlink.** `DELETE /link` also deletes this key.
- **Opting out is not retroactive.** A credential already sold stays valid until `expires_at`. The consent screen must say so.

## 7. Configuration

| Var | Example | Notes |
|---|---|---|
| `X402_FACILITATOR_URL` | `https://facilitator.ultravioletadao.xyz` | Empty disables the paid route (`503`) |
| `X402_ASSET` | `0x5425890298aed601595a70AB815c96711a31Bc65` | Must support EIP-3009, so **`tUSDC` does not work** |
| `X402_PRICE` | `5000` | Base units |

`pay_to` is not configured. It is read from `manager.treasury()`, so there is a single source of truth.

The CORS config must add `payment-signature` to the allowed headers, and expose `payment-required` and `payment-response`. Browser buyers stay limited to `ALLOWED_ORIGINS`; other servers and agents are the intended buyers and are not affected by CORS.

## 8. Local development

Plain Anvil has no Circle USDC, and `tUSDC` has no EIP-3009. So x402 work needs a **fork of Fuji**:

```bash
anvil --fork-url https://api.avax-test.network/ext/bc/C/rpc --port 8546
```

Then run the deploy script with `USE_CIRCLE_USDC=true`, and run a local facilitator, because public ones cannot see a fork. Test USDC on the fork comes from impersonating the token's `masterMinter`. A fork keeps chain id `43113`, so the domain and network names are the same as on Fuji.

## 9. Threats

Continues [`THREAT_MODEL.md`](THREAT_MODEL.md).

| # | Threat | Mitigation | Residual |
|---|---|---|---|
| D1 | Selling a student's data without consent | Off by default, signed opt-in, checked before payment | — |
| D2 | Replaying a payment signature | USDC rejects a reused EIP-3009 nonce, so `/settle` fails and no credential is returned | — |
| D3 | Buyer signs a lower amount or another recipient | Requirements are built by the Worker; the facilitator checks the payload against them | — |
| D4 | Getting the credential without paying | Returned only after `/settle` succeeds | — |
| D5 | Paying and getting nothing | Transfer settled but the Worker dies before responding | Small amount (0.005 USDC). Accepted |
| D6 | Forged credential | Signature must recover to an address holding `ORACLE_ROLE` | — |
| D7 | Oracle key leak mints false credentials | Admin revokes the role, which also invalidates old credentials; `expires_at` limits the rest | Buyers who skip the on-chain check stay exposed |
| D8 | Farming stats with **demo** challenges | `lms` field lets buyers reject `demo` links; creating challenges needs `CREATOR_ROLE` | See limitation 1 below |
| D9 | Linking `subject_hash` to a person | Same value as public evidence, contains no name | Moodle userids are small numbers, so someone who knows the site can guess a userid and test it. Inherited from evidence |
| D10 | Facilitator goes down or censors | Paid route fails closed, nothing is charged; we can self-host | — |
| D11 | Header or request flood | IP rate limit, 8 KB header cap, free checks before any facilitator call | — |

### Known limitations

1. **Stats mix demo and real challenges.** The badge has one counter per wallet, so a wallet linked to Moodle today may have earned its streak in demo challenges. The fix belongs to the contract or to a per-LMS count in the oracle. Until then, a credential is strongest on deployments without demo challenges.
2. **The oracle is trusted.** A credential is only as honest as the oracle, the same trust model as settlement. The roadmap is zkTLS.
3. **Self-attested facts stop at the LMS.** A credential proves an account completed work on time, not that the account's owner did the work.

## 11. Definition of Done

- `vitest`: `consent_message`, consent rules (default off, voided by relink, removed on unlink), the test vector, every row of the status table in section 3, requirements not taken from the buyer, credential not returned when `/settle` fails.
- One real payment on Fuji: USDC reaches the treasury, with a Snowtrace link.
- `/credential/verify` accepts a real credential and rejects a tampered one.
